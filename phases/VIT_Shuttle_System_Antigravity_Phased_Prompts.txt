VIT SHUTTLE SYSTEM
ANTIGRAVITY DEVELOPMENT PROMPTS
Phased implementation guide

PURPOSE
Use these prompts one phase at a time in Google Antigravity while working on the existing VIT Shuttle System project. The project is at an early stage, so inspect the codebase before making changes and build incrementally.

GENERAL WORKFLOW
1. Open the existing local project folder in Antigravity.
2. Before each phase, commit the current work to Git or create a checkpoint/branch.
3. Paste only the prompt for the phase you are working on.
4. Review the implementation in the browser and inspect errors.
5. Run available linting, type checking, tests, and build commands.
6. Fix regressions before moving to the next phase.
7. If data, APIs, credentials, or backend services are missing, document what is missing. Do not invent integrations or present sample data as real.
8. Keep a clear distinction between completed functionality, mock/sample data, and features that still require configuration.

GLOBAL INSTRUCTION TO INCLUDE WITH EVERY PHASE
Inspect the existing codebase first. Make the smallest coherent set of changes needed for this phase. Preserve completed work, reuse existing components, and do not rewrite unrelated parts of the application. After implementation, run the available checks and report what was actually completed versus what still requires configuration or additional development.

Do not rebuild the entire application from scratch unless genuinely necessary. Do not remove existing functionality simply to make a new feature easier. Do not claim that a feature, test, integration, or security control works unless it has actually been implemented and verified.

PHASE 4 — SMART JOURNEY PLANNER
============================================================

Build a journey planner for the existing VIT Shuttle System.

Inspect the existing route, stop, destination, and mapping implementations before making changes.

OBJECTIVE:
Help users plan journeys between configured campus locations using shuttle routes and walking connections.

USER FLOW:
1. Select a starting point.
2. Select a destination.
3. Optionally choose travel preferences.
4. Display suitable journey options.
5. Allow the user to select a journey.
6. Show the complete journey breakdown and route on the map.

JOURNEY RESULTS:
Each result should display:
- Starting point.
- Walking distance to the boarding stop.
- Estimated walking time.
- Boarding stop.
- Shuttle route.
- Waiting time, when available.
- Shuttle travel time, when available.
- Destination stop.
- Walking distance to the final destination.
- Total estimated journey duration.
- Data freshness and relevant uncertainty.

ROUTE PREFERENCES:
Support the following options where the underlying data permits:
- Fastest journey.
- Least walking.
- Fewest transfers.

ROUTE CALCULATION:
- Use configured stops, routes, route sequences, and travel information.
- Use a graph-based routing algorithm when appropriate.
- Account for walking connections between campus destinations and stops.
- Calculate transfer options only when the necessary route data exists.
- Use live arrival estimates only when reliable data is available.
- Clearly distinguish estimated values from verified schedules.

USER EXPERIENCE:
- Display journey steps in chronological order.
- Highlight the selected route on the map.
- Allow users to switch between available journey options.
- Include clear back navigation.
- Support swapping the starting point and destination.
- Allow saving frequently used journeys.
- Provide useful messages when no suitable route is available.

IMPORTANT:
Do not invent routes, stops, schedules, or walking paths.
If the required data is missing, create an appropriate data model and clearly identify the missing configuration rather than pretending that a complete route calculation is possible.
Keep the implementation modular so that additional routing algorithms and data sources can be added later.

Test journey selection, missing-data handling, and responsive layouts.

PHASE 10 — SMART CROWD PREDICTION AND ANALYTICS
============================================================

Extend the VIT Shuttle System with a foundation for shuttle occupancy monitoring and transportation analytics.

First inspect the existing database, trip records, passenger records, and available operational data.

Do not assume historical passenger counts already exist.

PART A: OCCUPANCY
Create a suitable structure for recording:
- Vehicle capacity.
- Reported passenger count.
- Occupancy status.
- Timestamp.
- Associated vehicle and trip.
- Data source.

Support manual occupancy reporting as an initial implementation if automatic passenger counting is unavailable.
Clearly identify manually reported, estimated, and sensor-derived occupancy data.

PART B: ANALYTICS DASHBOARD
Where the underlying records exist, display:
- Trips per day.
- Route usage.
- Passenger counts.
- Average reported delays.
- Route demand by time of day.
- Vehicle utilization.
- Data freshness and completeness.

PART C: CROWD ESTIMATION
Design a future-ready approach to estimating occupancy levels.
Begin with transparent rules or statistical methods where appropriate.
If sufficient historical data becomes available, evaluate whether a forecasting model would improve predictions.
Do not claim that a predictive model is accurate without testing it against held-out historical data.

PART D: VISUALIZATION
Use clear charts and tables with descriptive titles, units and time ranges, empty states, loading states, accessible labels, and clear explanations of estimates.

PART E: DATA QUALITY
- Validate incoming passenger counts.
- Prevent impossible negative counts.
- Compare counts against configured vehicle capacity.
- Track when measurements were collected.
- Distinguish missing data from zero passengers.
- Avoid double-counting repeated events.

PART F: PRIVACY
Prefer aggregated statistics over identifiable passenger histories.
Do not collect personal information unless it is necessary for a clearly defined feature.

DELIVERABLES:
Implement the analytics components that can be supported by existing data, document missing data requirements, and keep the system ready for future forecasting.
